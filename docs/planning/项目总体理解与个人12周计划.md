# Azure 客户流失预测与 CLV 提升：项目理解与个人 12 周计划

> 编写日期：2026 年 8 月 31 日  
> 文档定位：这是基于项目 brief 的个人理解与执行计划，不是已经完成的数据分析报告。文中的模型指标和 ROI 数字属于验收目标，最终结果必须以实际数据和独立测试为准。

## 一、我对项目总体的理解

### 1. 项目的本质

这个项目不是单纯训练一个“客户是否流失”的分类模型，而是要建立一条从业务问题到留存行动的完整分析链路：

```text
理解业务和定义口径
        -> 检查数据是否可信
        -> 预测谁可能流失
        -> 解释为什么可能流失
        -> 判断客户未来价值
        -> 决定先干预谁、采取什么行动
        -> 用实验或因果方法验证行动是否有效
        -> 计算收益、成本和 ROI
```

最终目标不是得到一个漂亮分数，而是让客户成功团队能够回答四个实际问题：

1. **谁可能流失？** 给每位客户一个经过校准的风险概率。
2. **为什么可能流失？** 找到整体和单个客户的主要风险因素。
3. **谁最值得优先处理？** 将流失风险与 CLV、毛利和干预成本结合。
4. **怎样证明挽留有效？** 通过 A/B 测试、uplift 或因果推断估计增量效果。

### 2. 从业务问题到分析产出

| 业务问题 | 分析方法 | 主要产出 |
| --- | --- | --- |
| 哪些客户可能离开 | 分类模型、概率校准、阈值分析 | 客户级流失概率和风险等级 |
| 哪些因素推高风险 | EDA、SHAP、LIME、分群比较 | 全局驱动因素和单客原因 |
| 哪些客户最重要 | RFM、行为分群、CLV | 风险-价值矩阵和优先名单 |
| 应采取什么行动 | 驱动因素到策略映射、成本收益分析 | 分层留存策略和行动手册 |
| 行动是否值得 | A/B 测试、因果推断、敏感性分析 | 增量留存、增量 CLV 和 ROI |

### 3. 数据在本项目中的位置

PDF 推荐的 Telco Customer Churn 数据适合练习端到端流程，但它是电信代理数据，不是微软内部 Azure 客户数据。我的实现将分成两层：

- **MVP 层**：先用 Telco 数据完成数据质量检查、EDA、基线模型、解释和简化风险-价值分析。
- **进阶层**：只有在获得合法且时间口径一致的数据后，才加入云资源使用趋势、工单、交易序列、时间切分、正式 CLV 和因果评估。

在任何分析开始前，都必须固定以下定义：

- 一行数据代表客户、企业账号、订阅还是资源组。
- 哪一天是观察截止日，预测未来多少天。
- 什么情况算流失，是否有宽限期和标签延迟。
- 收入、毛利、贡献利润和 CLV 使用哪一种价值口径。
- 哪些字段在预测时已经可知，哪些属于未来信息或泄漏。

### 4. 我对“项目成功”的判断

我会从四个层面判断项目是否成功：

1. **数据可信**：数据来源、字段含义、质量问题和处理规则都有记录。
2. **模型可信**：切分方式合理，无数据泄漏；同时报告 AUC、PR-AUC、F1、召回率、精确率、校准和分群表现。
3. **业务可用**：风险分数能够对应客户、原因、价值、行动和负责人，而不是停留在 Notebook。
4. **效果可证**：明确区分相关性、预测效果和干预的因果效果，并报告成本、不确定性和限制。

brief 给出的基线 AUC-ROC 0.75、优化模型 AUC-ROC 0.88、F1 0.80 和策略 ROI 300% 都是目标线。若真实数据无法达到，应如实解释原因，不通过泄漏、反复查看测试集或修改标签来凑指标。

### 5. 主要风险与应对原则

| 风险 | 可能后果 | 我的处理原则 |
| --- | --- | --- |
| 代理数据被误写成 Azure 真实数据 | 结论失真，报告可信度下降 | 在标题、数据字典和结论中持续标注代理数据 |
| 标签和预测窗口不清楚 | 模型问题本身被定义错 | 第 1 周冻结数据合同，变更必须留版本记录 |
| 时间或目标泄漏 | 离线分数虚高 | 以观察截止日审查每个特征，预处理仅在训练集拟合 |
| 类别不平衡 | 只预测多数类也显得准确 | 使用 PR-AUC、召回率、阈值和成本共同评估 |
| 强行拼接不同公开数据 | 产生虚假的客户关系 | 无稳定键和时间口径就分开分析 |
| 把相关性当成干预效果 | 高风险策略可能无效或有害 | 用随机实验或明确因果假设估计增量效果 |
| 云资源产生费用 | 超出个人预算 | 本地完成 MVP；上云前设置预算、标签和清理规则 |

## 二、我对第一周任务的理解

### 1. 第一周真正要解决的问题

第一周不是急着训练模型，而是回答三个基础问题：

1. **业务问题是否定义清楚？** 明确客户、流失、预测时间和价值的含义。
2. **数据是否足以回答问题？** 看懂每列、确认来源，并系统发现质量问题。
3. **后续 11 周是否可执行？** 把任务、依赖、验收标准和风险写成路线图。

如果这一步含糊，后面的模型越复杂，返工和错误结论越多。因此第一周的核心产出是“统一口径和建立可信起点”。

### 2. Brief 要求的三类交付物

| 交付物 | 我对内容的理解 | 完成标准 |
| --- | --- | --- |
| 《Azure 云服务业务与客户流失分析报告》 | 说明商业模式、客户旅程、流失机制、关键指标和待验证因素 | 至少提出 8 个有业务依据、可以被数据验证的因素 |
| 《数据质量评估报告》 | 记录数据来源、粒度、字段、缺失、重复、类型、范围、异常和逻辑冲突 | 问题有数量、比例、样例、严重度和处理建议，不只写“已检查” |
| 整体路线图 | 将 12 周目标拆成里程碑、依赖、风险和完成定义 | 每周有输入、动作、输出、检查点和风险应对 |

### 3. 第一周的四个工作包

#### 工作包 A：业务与客户流失研究

我会先理解 Azure 场景中的客户旅程：试用或购买、上手、资源采用、使用扩张、续约、降配或取消。研究内容包括订阅与按量付费、合同周期、支持服务、客户成功和云成本管理。

第一周至少形成以下 10 个**待验证假设**，它们不是结论：

1. 月付或短合同客户的流失风险可能高于长期合同客户。
2. 新客户在上手早期使用不足时更容易流失。
3. 近 30/90 天使用量持续下降可能早于正式取消。
4. 使用的服务种类少、关键功能采用浅可能代表粘性不足。
5. 费用快速上升但使用价值没有同步增长可能增加流失风险。
6. 支付失败、欠费或账单争议可能是短期风险信号。
7. 工单频繁、严重或解决时间长可能降低续约意愿。
8. 自动续费设置、历史续约次数可能影响流失概率。
9. 行业、地区和企业规模可能改变客户对价格和支持的敏感度。
10. 高风险因素在高价值与低价值客户中可能有不同的干预优先级。

#### 工作包 B：数据理解与数据合同

我会为 Telco 代理数据建立字段字典，至少记录：字段名、中文含义、数据类型、单位、允许值、缺失规则、业务可用时间和是否可能泄漏。

同时写出数据合同初稿：

- 主体粒度：一行代表一个客户。
- 唯一键：确认 `customerID` 是否唯一且非空。
- 标签：确认 `Churn` 的原始取值和转换规则。
- 时间限制：Telco 数据缺少完整快照时间，因此 MVP 不能假装完成严格时间切分。
- 价值字段：明确 `MonthlyCharges`、`TotalCharges` 的含义和局限。
- 数据来源：记录下载地址、下载日期、许可和文件哈希。

#### 工作包 C：数据质量评估计划

数据质量检查不只是调用 `info()`，而是为每类问题留下可复核证据：

| 检查维度 | 具体检查 | 输出 |
| --- | --- | --- |
| 文件与结构 | 文件能否读取、编码、行列数、列名 | 数据概况表 |
| 唯一性 | 客户 ID 为空或重复 | 重复记录清单 |
| 完整性 | 各列缺失数量、比例和缺失组合 | 缺失率表和热图 |
| 类型 | 数字被读成字符串、日期格式不一致 | 类型问题清单 |
| 合法范围 | 负费用、非法月份、异常类别 | 越界记录清单 |
| 一致性 | 总费用与服务年限矛盾、服务组合冲突 | 逻辑规则及命中数量 |
| 异常值 | 费用、服务数量等极端值 | 分布、箱线图和待确认样本 |
| 标签质量 | 标签比例、未知值、潜在重复标签 | 标签审计表 |
| 泄漏风险 | 预测时不可知或由标签直接产生的字段 | 泄漏审查清单 |

每个问题都要记录严重度、影响范围、可能原因、建议动作和是否需要业务确认。第一周只提出处理建议，不应在没有依据时直接删除异常客户。

#### 工作包 D：路线图与风险登记

我会把 brief 的 12 周计划转成自己的可执行任务，并建立风险登记表。优先记录：数据获取失败、字段不匹配、时间字段不足、模型指标不达标、算力和 Azure 费用、隐私与发布风险。

以下按每天约 2-3 小时、全周约 16 小时安排：

### 5. 第一周完成定义（Definition of Done）

第一周结束时，我要能够拿出证据回答：

- 数据来自哪里，能否合法用于学习和展示？
- 一行代表谁，客户 ID 是否唯一，标签是什么意思？
- 所有列的数据类型、含义、单位、取值范围和预测可用时间是什么？
- 缺失、重复、异常、非法类别和逻辑冲突各有多少？
- 至少 8 个业务因素如何映射到可检查字段或数据缺口？
- 哪些问题会阻挡建模，哪些可以在后续清洗时处理？
- 未来 11 周每周要交付什么，主要依赖和风险是什么？

第一周的非目标是：不追求最终模型分数，不强行合并三个公开数据集，不虚构 Azure 内部字段，也不把初步相关性写成因果结论。

## 三、我的个人 12 周计划

### 1. 时间和工作方式假设

我暂按每周 15-18 小时规划：学习与查资料约 20%，编码与实验约 45%，分析与文档约 25%，复盘与项目管理约 10%。如果某周时间减少，优先保证可复现的主流程和真实记录，删减高级加分项，不牺牲数据质量和独立测试。

| 周次 | 核心目标 | 我的主要行动 | 完成标志 |
| --- | --- | --- | --- |
| 第 1 周 | 冻结问题与数据起点 | 业务研究、数据合同、字段字典、数据质量检查、路线图和风险表 | 3 份第一周交付物完成 v1；至少 8 个因素；质量问题有数量和建议 |
| 第 2 周 | 看懂流失模式 | 完成单变量和多变量 EDA；建立客户画像；提出可验证假设；制作 Power BI 初版 | 至少 15 个有效图表、5 个假设；图表有问题、结论和限制 |
| 第 3 周 | 建立可复用清洗流程 | 将类型修复、缺失处理、编码和标准化放入脚本/Pipeline；写数据测试 | 一条命令生成处理数据；无硬编码路径；关键质量规则通过 |
| 第 4 周 | 构建可解释特征集 | 增加服务、费用、交互、聚合和代理时间特征；比较特征选择方法 | 至少 50 个有定义的候选特征；来源、公式和泄漏审查完整 |
| 第 5 周 | 建立可信基线 | 设计适合数据条件的切分；训练逻辑回归和决策树；比较类别权重与采样 | 基线报告含 AUC、PR-AUC、F1、召回率、校准和混淆矩阵 |
| 第 6 周 | 优化模型但控制过拟合 | 训练三个 Boosting 模型；用 Optuna 调参；比较细分市场表现 | 固定验证流程；保存最优 Pipeline；如实说明与目标线的差距 |
| 第 7 周 | 让模型可解释、可使用 | 做全局和单客 SHAP/LIME；校准概率；设计风险等级和评分卡 | 前 10 个驱动因素、典型客户解释、明确风险阈值和使用限制 |
| 第 8 周 | 连接风险与客户分群 | 构造代理 RFM；比较 K-Means 与 DBSCAN；建立风险-价值四象限 | 分群稳定性和业务含义可解释；输出优先客户群及边界 |
| 第 9 周 | 估算 CLV 与留存价值 | 先检查交易/频次假设；条件满足时用 BG/NBD 和 Gamma-Gamma，否则使用透明的订阅简化式 | 客户级 CLV、群体对比、假设清单和留存提升情景表 |
| 第 10 周 | 设计可验证的留存行动 | 将驱动因素映射到至少 5 种策略；估算成本；设计 A/B 测试与样本量 | 策略手册、成本表、实验单位、主指标、护栏指标和停止规则齐全 |
| 第 11 周 | 比较策略组合与不确定性 | 模拟至少 10 个组合；对效果、成本和折现做敏感性分析；估算 ROI 区间 | 不只报告单点 ROI；给出推荐组合、适用客户和失败条件 |
| 第 12 周 | 形成可复现交付 | 清理仓库；补 README、数据卡、模型卡；完成报告、PPT、Power BI 和演示 | 新环境可按说明复现；结果、限制和伦理边界一致；完成最终检查表 |

### 2. 每周固定节奏

为了防止只写代码、不形成成果，我每周采用相同节奏：

1. **周初定义**：写清本周问题、输入、输出和不做什么。
2. **周中实现**：先完成最小可运行版本，再增加复杂度；每天保留运行记录。
3. **周中检查**：审查数据泄漏、随机种子、切分、指标和文件路径。
4. **周末交付**：整理 Notebook、脚本、图表和文字结论，对照验收表自查。
5. **周末复盘**：记录已完成、未完成、风险、下周依赖和一个最重要改进点。

### 3. 每周都要保留的证据

- 可重复运行的命令和环境版本。
- 输入数据来源、处理步骤和输出路径。
- 指标表、图表、随机种子和实验配置。
- 失败实验及原因，而不只保留最好结果。
- 业务结论对应的图表或统计证据。
- 已知限制、仍需确认的问题和下一周输入。

## 四、暂停结束后的第一步

恢复项目时，我将先执行以下动作，而不是继续安装新工具：

1. 创建标准项目目录。
2. 下载 Telco Customer Churn 数据并登记来源与文件哈希。
3. 建立第一版数据字典和数据合同。
4. 编写只读的数据质量检查 Notebook 或脚本。
5. 按第一周完成定义整理三份交付物。

环境只有在验证失败或新任务确实需要新组件时才调整。所有后续工作都以“数据可信、过程可复现、结论不过度”为基本原则。
