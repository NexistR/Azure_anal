## 一、第一周结论

### 1. 周目标

在不急于训练模型的前提下，冻结业务和数据口径，建立可审计的数据起点，并把后续 7 周拆成有输入、动作、输出、检查点和风险应对的可执行路线图。

第一周必须回答：

1. 业务问题是否定义清楚：客户、流失、预测时间和价值分别指什么。
2. 当前数据是否足以回答问题：来源是否合法、字段能否支撑假设、有哪些质量和时间限制。
3. 后续工作是否可执行：哪些依赖已经满足，哪些事项会阻塞 EDA、清洗、建模、解释或风险-价值分群。

### 2. 业务问题主线

8 周范围内完成前三个问题的分析闭环，并为第四个问题保留方法边界：

| 业务问题 | 后续分析 | 第一周要准备的口径 |
| --- | --- | --- |
| 谁可能流失 | 校准的客户级风险概率和风险等级 | 客户粒度、Churn 标签、观察截止日、预测窗口 |
| 为什么可能流失 | EDA、模型解释和客户级原因码 | 10 个待验证假设、字段映射、相关性与因果边界 |
| 谁值得优先处理 | 风险 × 可用价值代理、客户分群 | 价值代理口径、Telco 数据限制、风险-价值四象限 |
| 怎样证明挽留有效（范围外接口） | A/B、uplift 或因果评估 | 本项目只记录所需数据和限制，不在 W1–W8 实施 |

### 3. 四条工作流

| 工作流 | 本周任务 | 本周产出 |
| --- | --- | --- |

| C. 可复核质量审计 | 只读原始数据，系统检查结构、唯一性、完整性、类型、范围、一致性、异常、标签和泄漏 | 质量检查脚本/Notebook、质量结果表、数据质量评估报告 v1 |

## 二、执行前提与范围边界

### 1. 当前起点

- Python、Jupyter、Pandas、建模、解释、CLV、因果、Spark、VS Code、Git、Power BI Desktop 和 Azure CLI 已完成阶段性安装与验证；正常情况下不重复安装。CLV 和因果工具可用不代表相关任务进入本项目八周范围。
- 当前已完成三个 Kaggle 原始数据集的下载、解压和哈希登记；仍未完成 `az login`/订阅和资源、Power BI 在线发布、Git 作者/远程仓库和首次提交；项目基础目录已建立。
- 第一周的云登录、Power BI 在线发布和 GitHub 连接不是硬依赖；数据获取、许可确认和本地文件登记是质量审计的硬依赖。

### 2. 数据与表述边界

- Telco Customer Churn 仅作为公开电信代理/教学数据，不能写成 Azure 内部真实客户数据。
- Support Tickets、SaaS 或其他公开数据没有共同客户 ID、时间口径和标签时，分开分析，不强行拼接。
- Telco 缺少完整快照时间，因此第一周必须把“严格时间切分不可用”登记为风险；不能伪造观察截止日，也不能把随机切分写成时间验证。
- `Churn` 是标签，不进入特征；任何由标签产生、发生在观察截止日之后或包含取消结果的字段都标记为潜在泄漏。
- 本周只提出修复建议，不无依据删除异常客户；原始数据只读，处理结果写入 `data/processed/`。
- brief 中的 AUC、F1、ROI 等数字是目标线或背景，不是当前实测结果；本项目可评估 W5–W7 的模型指标，但不承诺八周内验证实测 ROI，也不通过泄漏、改标签或重复查看测试集来追指标。

### 3. 范围与工时选择

- 执行基线固定为 W1–W8，每周约 15–18 小时，第一周约 2–3 小时/天。
- 原 12 周材料只用于引用 W1–W8 的任务与技术边界，不自动带入 W9–W12。
- 历史专项 PDF 是 8 周、25–30 小时/周，配套 DOCX 是 8 周、15–18 小时/周；本项目采用较可持续的 15–18 小时。若实际投入时间改变，只调整每周范围和优先级，不改变 DoD 与数据治理红线。

## 四、七天推进步骤

### D1：范围确认与启动门 G0（约 2–3 小时）

**目标**：把“做什么、用什么数据、暂时不做什么”写成单页范围说明。

**步骤**

1. 重读项目 brief、交接文件和 8 周范围声明，摘录本周验收标准。
2. 写出一句话目标：基于公开 Telco 代理数据建立可信的数据与业务起点，为后续流失预测和价值决策提供可复核依据。
3. 写明代理数据声明、项目四问、MVP/进阶边界和本周非目标。
4. 建立术语表：客户/账号/订阅、流失、观察截止日、预测窗口、MonthlyCharges、TotalCharges、价值代理和风险；CLV、增量效果、ROI 标为范围外的未来扩展术语。
5. 建立问题清单和决策日志，记录未决的客户粒度、标签窗口、时间字段、价值口径和数据许可。

**当日证据**：`scope_v1.md`、`glossary_v1.md`、`decision_log.md`、启动检查记录。

**通过条件 G0**：代理声明、目标、非目标和关键术语已写清；客户、流失、窗口或价值任一项未决时，明确标记为阻塞，不进入模型。

### D2：业务研究与假设门 G1（约 2–3 小时）

**目标**：把 Azure 客户旅程和流失机制转换为可验证的分析假设。

**步骤**

1. 梳理试用/购买、上手、资源采用、使用扩张、续约、降配/取消、支持和账单等阶段。
2. 研究订阅/按量付费、合同周期、Customer Success、成本管理和账单支付等业务机制，并补充行业流失预防/客户成功最佳实践；每条外部事实保留来源。
3. 建立 10 项假设矩阵，每项填写：业务依据、可映射字段、验证指标、后续 EDA/模型方法、数据缺口、是否可行动。
4. 至少保留 8 项“有业务依据且可被数据验证”的因素；“无法验证”要写成数据缺口而不是结论。

**建议假设**

| 编号 | 待验证假设 | 首选字段/缺口 |
| --- | --- | --- |
| H1 | 月付或短合同客户流失风险更高 | `Contract` |
| H2 | 新客早期上手或使用不足预示流失 | `tenure`；缺早期时间序列 |
| H3 | 近 30/90 天使用下降早于取消 | 缺用量时间序列 |
| H4 | 服务种类少或关键功能采用浅的客户风险更高 | 服务订阅列；缺功能深度 |
| H5 | 费用上涨但感知价值未同步时风险更高 | `MonthlyCharges`、服务字段；缺价值指标 |
| H6 | 支付失败、欠费或账单争议提高风险 | `PaymentMethod`、账单字段；缺事件记录 |
| H7 | 工单频繁、严重或解决慢提高风险 | 缺稳定客户 ID/时间，暂不合并工单 |
| H8 | 自动续费和历史续约降低/改变风险 | 缺自动续费、续约历史 |
| H9 | 行业、地区和规模改变价格/支持敏感度 | Telco 字段可能缺失，不能伪造 |
| H10 | 同一风险因素在高价值与低价值客户中的优先级不同 | 价值代理 + 风险交叉 |

**当日证据**：业务旅程图或文字流程、来源清单、`hypothesis_matrix_v1.csv/md`、业务报告目录。

**通过条件 G1**：每项假设已标记“可验证/需新增数据/当前不可验证”，至少 8 项可绑定字段和后续方法。

### D3：数据获取、登记与版本门（约 2–3 小时）

**目标**：获得可合法使用的 Telco 原始文件，并让任何人能够复核文件版本。

**步骤**

1. 创建标准目录：`data/raw/`、`data/processed/`、`notebooks/`、`src/`、`reports/`、`dashboard/`、`tests/`；必要时在忽略目录内保留本地 README。
2. 按来源说明下载 Telco、Customer Support Tickets 和 SaaS 数据，分别放入对应子目录；若账号、许可或下载受阻，立即记录阻塞，不用未经确认的替代文件冒充同一版本。
3. 记录来源 URL、发布者、许可/使用条件、下载日期、文件名、文件大小、编码、版本、本地路径和 SHA-256；Telco 作为主练习数据，其余数据集先分开分析。
4. 用 `Get-FileHash -Algorithm SHA256 <file>` 或等价工具计算哈希；保留命令和输出。
5. 确认原始目录只读，检查 `.gitignore` 不会把客户数据或密钥提交到 Git。

**当日证据**：`data_manifest.csv/md`、哈希输出、许可截图或链接、目录树、下载日志。

**通过条件 G2-A**：来源和许可可解释、文件版本可复核、原始数据在本地可读取；否则把“数据获取/许可未确认”列为 P0 阻塞项，暂停质量结论。

### D4：字段理解与数据合同门（约 2–3 小时）

**目标**：明确每列代表什么、何时可用、能否支撑业务假设。

**步骤**

1. 在只读副本上记录行数、列数、列名、编码、原始 dtype 和示例值。
2. 检查 `customerID` 空值和重复；统计 `Churn` 原始取值并写出转换规则。
3. 为每一列补齐：字段名、中文含义、数据类型、单位、允许值、缺失规则、业务可用时间、潜在泄漏标记、对应假设。
4. 明确 `MonthlyCharges`、`TotalCharges` 的含义和局限；不把它们直接称为毛利或正式 CLV。
5. 登记 Telco 没有完整时间快照的事实，并在合同中写明 MVP 不能做严格时间切分。
6. 写出合并规则：无稳定共同 ID 和一致时间口径时，Telco、工单、SaaS 分开分析；若未来合并，必须先聚合并用 `merge(validate=...)` 防止行膨胀。

**当日证据**：`data_dictionary_v1.csv/md`、`data_contract_v1.md`、原始概况表、ID/标签统计。

**通过条件 G2-B**：粒度、主键、标签、窗口/时间限制、价值口径、字段可用性、来源和泄漏标记齐全；未决项进入风险登记。

### D5：可复核质量审计与质量门 G3（约 2–3 小时）

**目标**：用一次可重复运行的脚本或 Notebook 生成质量基线，而不是只手工查看几行。

**步骤**

1. 建立 `notebooks/01_data_profile.ipynb` 或 `scripts/profile_data.py`；输入路径、输出路径和随机种子集中配置。
2. 检查文件可读性、编码、行列数、列名和异常解析。
3. 检查 ID 空值/重复、整行重复，以及各列缺失数量、比例和缺失组合。
4. 检查数字列被读成字符串、日期/货币解析、非法类别、负费用、非法月份和取值范围。
5. 检查业务逻辑：`TotalCharges` 与 `tenure` 的矛盾、服务组合冲突、费用与服务状态不一致。
6. 输出费用、服务数等数值的分布、分位数、箱线异常和代表性样例；异常先标记，不直接删除。
7. 检查 `Churn` 比例、未知值、标签重复和潜在标签泄漏；记录类别不平衡对后续评估的影响。
8. 让脚本输出机器可读结果和运行日志，确保换路径后仍可复现。

**质量问题登记格式**

每条命中至少包含：规则、字段、数量、比例、样例（脱敏）、严重度、影响范围、可能原因、建议动作、是否需业务确认、责任人、状态。

| 质量维度 | 最低检查 | 阻塞判定示例 |
| --- | --- | --- |
| 结构/可读性 | 文件、编码、行列、列名、解析错误 | 文件不可读或列错位 |
| 唯一性 | 主键空值、重复 ID、重复行 | 无法确定分析单位 |
| 完整性 | 各列缺失数/比例/组合 | 标签或主键大面积缺失 |
| 类型/格式 | 数字、日期、货币、类别解析 | 关键字段无法转换 |
| 合法范围 | 负值、非法月份、未知类别 | 关键业务值越界且无法解释 |
| 逻辑一致性 | 费用、年限、服务组合关系 | 大量互相矛盾且影响标签 |
| 异常值 | 分位数、箱线、样例 | 不删除，先确认业务原因 |
| 标签质量 | 取值、比例、未知、重复标签 | 标签定义或窗口不明 |
| 泄漏/时间/漂移 | 标签派生列、未来字段、时间可用性；有多版本时比较分布漂移 | 任何特征使用未来信息；无时间/版本时记录“无法评估” |

**当日证据**：质量脚本/Notebook、运行日志、`data_quality_results.csv/md`、质量问题登记表。

**通过条件 G3**：九类检查均有结果；每类问题都有数量、比例、样例、严重度和建议；阻塞项与可后续处理项已分开。

### D6：报告初稿与影响分级（约 2–3 小时）

**目标**：把事实、限制和建议写成可审阅的两份报告初稿。

**步骤**

1. 将 10 假设、客户旅程、业务指标和字段缺口写入业务报告。
2. 将来源、粒度、字段概况、质量统计和问题登记表写入质量报告。
3. 按 P0 阻塞、P1 必须在建模前处理、P2 可在后续迭代处理分级；每项写影响和建议负责人。
4. 对每个结论附证据路径、运行时间、数据版本和限制；没有数据支持的 Azure 字段写成“待获取/不可验证”。

## 七、风险与阻塞登记规则

| 风险/阻塞 | 触发器 | 本周应对 | 后续应急路径 |
| --- | --- | --- | --- |
| 数据获取或许可失败 | 下载失败、许可不明、哈希无法复核 | D3 记录 P0，不产出质量结论 | 获取授权或更换经确认的公开版本，重新登记版本 |
| 代理数据误写 Azure | 报告把 Telco 字段写成 Azure 内部事实 | 所有标题、字典、结论加代理声明 | 重写结论，拆分“业务依据”和“数据证据” |
| 粒度/ID 不清或重复 | `customerID` 为空/重复，无法确定一行代表谁 | D4 阻塞合同和模型 | 业务确认粒度；必要时改为聚合级分析 |
| 标签/观察窗口不清 | Churn 定义、宽限期或标签延迟未知 | 冻结为未决项，不进入模型 | 获取真实时间和标签规则；否则只做静态代理分类 |
| 无时间字段 | Telco 无完整快照时间 | 登记无法严格时间切分 | W5 报告限制；有真实时序数据后再升级 |
| 跨数据集伪关联 | 无共同 ID/时间口径却尝试 merge | 本周分开分析 | 先建立合法统一键和聚合规则再合并 |
| 质量问题影响标签/关键特征 | 大面积缺失、非法值或逻辑冲突 | P0/P1 分级并要求确认 | 修复规则、保留版本、重跑质量审计 |
| 类别不平衡或指标不达标 | 流失比例低、PR-AUC/召回不足 | 仅登记影响，不提前调参 | W5 比较多种训练折内处理和成本阈值 |
| 云费用/账号权限 | Azure 未登录、无预算或需付费资源 | 本地 MVP；不把登录设为 W1 硬依赖 | 预算告警、资源标签、到期清理后再上云 |
| 隐私或误提交 | 原始客户数据、密钥进入 Git | `.gitignore`、提交前扫描、原始只读 | 立即停止发布并按仓库安全流程处理 |
| 超出八周范围 | 把正式 CLV、实验、ROI 或 W9–W12 加入当前待办 | 路线图只保留 W1–W8 | 范围外需求另立项目，不阻塞 W8 验收 |
| 工时口径冲突 | 15–18h/25–30h 口径混用 | 固定采用 15–18h/周并记录 | 只调整周内优先级，不降低 DoD 和红线 |

每条风险都要有 `owner`、状态、触发器、缓解措施、应急措施和下次复查日期。没有 owner 的风险视为未管理。
