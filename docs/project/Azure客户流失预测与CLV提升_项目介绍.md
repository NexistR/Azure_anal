# 微软 Azure 云服务客户流失预测与全生命周期价值提升分析

## 文档说明

本文根据工作区中的项目 brief《微软数据分析实习项目：微软 Azure 云服务客户流失预测与全生命周期价值提升分析(1).pdf》整理，共 5 页。它介绍的是一个项目设计和验收要求，不是已经完成的项目报告。

文中出现的收入增速、流失率、AUC、F1、ROI 等数字，除非特别注明，都是 brief 中的背景信息或目标值。PDF 没有提供微软内部客户原始数据、字段字典、模型输出或实测结论，因此不能把这些目标值写成已经取得的结果。

## 一句话概览

用客户行为数据回答四个问题：**谁可能流失、为什么流失、这个客户未来值多少钱、采取什么留存行动最划算**。项目以微软 Azure 全球客户成功团队（Customer Success Team）的工作场景为背景，把数据分析、机器学习、客户分群、客户全生命周期价值（CLV）和实验评估串成一条可执行的流程。

## 1. 项目背景与业务问题

### Brief 给出的背景

以下内容是项目 brief 的情境设定；正式对外发布前应以可核验的业务数据和统计口径重新确认。

来源：PDF 第 1 页。

| 背景信息 | 对项目的含义 | 说明 |
| --- | --- | --- |
| Azure 在 brief 中被描述为全球第二大公有云服务提供商 | 客户规模和服务复杂度使客户成功管理具有代表性 | 这是 brief 的背景陈述，正式报告应核验排名口径 |
| Azure 云服务收入在 brief 所述的 2026 财年 Q1 同比增长 28% | 业务仍在增长，但增长不能只依靠拉新 | 这是 brief 的背景陈述，需在正式报告中注明来源和统计口径 |
| 中小企业（SMB）客户流失率被设定为 18.7% | SMB 是优先分析的细分市场 | 需要先确认“流失”的时间窗口和分母 |
| 获取新客户的成本约为保留老客户的 5-7 倍 | 预测和干预流失可能比单纯拉新更有经济价值 | 需结合公司的真实成本口径复核 |
| 留存率提升 5% 可能带来 25%-95% 的利润提升 | 可以用 CLV 和成本收益模型量化留存价值 | 这是行业背景范围，不是本项目的实测效果 |

### 要解决的业务问题

1. 在客户真正取消服务前，找出高风险客户，并给出可解释的流失概率。
2. 找出影响流失的关键因素，例如使用下降、服务体验、合同和价格等。
3. 同时考虑流失风险和客户价值，优先处理“高价值、高风险”客户。
4. 估算每位客户的预期剩余价值，以及挽留后的增量价值。
5. 为不同原因和客户群设计有成本预算的干预方案。
6. 用 A/B 测试或因果推断验证干预是否真的降低了流失，而不是只观察相关性。

### 可优先验证的业务因素

下面是满足“至少识别 8 个关键因素”目标的一组起点，不代表这些因素已经被数据证明：

1. 合同类型和续约距离。
2. 服务年限和新客上手阶段。
3. 近 7/30/90 天的活跃度、API 调用或资源使用趋势。
4. 功能采用数量和使用深度。
5. 月收入、毛利、折扣和增长趋势。
6. 客服工单数量、优先级和解决时长。
7. 账单、支付失败和欠费情况。
8. 地区、行业、企业规模等客户属性。
9. 订阅/资源数量和服务组合。
10. 自动续费设置与历史续约行为。

最终应通过 EDA、模型解释和实验逐项验证；相关性强不等于干预一定有效。

### 业务问题到分析问题的转换

| 业务问题 | 可量化的分析问题 | 产出 |
| --- | --- | --- |
| 谁会流失？ | 在约定的预测窗口内，客户流失概率是多少？ | 客户级风险分数 |
| 为什么流失？ | 哪些特征对整体和单个客户的预测贡献最大？ | SHAP/LIME 解释、驱动因素报告 |
| 先服务谁？ | 流失概率和 CLV 组合后，哪些客户的预期增量收益最大？ | 风险-价值四象限 |
| 做什么挽留？ | 哪项行动对哪类驱动因素有效，成本是多少？ | 分层策略手册、成本收益表 |
| 是否有效？ | 与不干预相比，行动带来的留存和 CLV 增量是多少？ | A/B 结果或模拟结果 |

## 2. 端到端分析流程

```text
业务理解与指标定义
        -> 数据获取、数据质量检查
        -> EDA 与客户画像
        -> 清洗、编码、特征工程
        -> 时间切分与流失预测
        -> 模型解释与风险分层
        -> RFM/行为分群与风险-价值矩阵
        -> CLV 预测与留存收益估算
        -> 差异化干预、A/B 设计
        -> 效果模拟、敏感性分析与 ROI 优化
        -> 报告、仪表板和可复现交付
```

### 项目边界与需要先确认的定义

PDF 没有指定以下口径。正式开始前应写入项目 README 或数据合同，所有后续指标都沿用同一版本：

- **客户粒度**：个人、企业账号、订阅还是资源组。Azure 场景通常建议以 account/subscription 为主要粒度。
- **观察截止日**：用哪些历史数据预测，数据更新频率是日、周还是月。
- **预测窗口**：例如未来 30、60 或 90 天内是否流失。示例窗口只是实施建议，不是 PDF 的既定值。
- **流失标签**：取消订阅、连续欠费、长期无活跃，还是客服确认离开。必须规定宽限期和重复取消如何处理。
- **价值口径**：收入、毛利、贡献利润或 CLV；是否扣除支持、折扣和干预成本。
- **可行动性**：模型分数必须能映射到具体客户经理或自动化触达动作。

| [SaaS Customer Churn Dataset](https://www.kaggle.com/datasets/wearetenet/saas-churn-rate-statistics-dataset) | 做 SaaS 与云服务流失模式的对比 | 含订阅和使用数据 |

### 使用这些数据时要诚实标注

Telco 数据是公开的电信客户流失数据，不是微软内部 Azure 数据。它可以作为**代理数据（proxy）**来练习流程，但不能据此声称得到了微软客户结论。PDF 提议扩展的虚拟机使用时长、存储使用量、API 调用次数等字段，如果没有真实来源，应标为“模拟/教学字段”，并在结果中单独说明。

三个数据集通常没有可直接对应的统一客户 ID、时间范围和标签定义。不能按行号或客户姓名强行拼接。可选做法是：

1. 先只用 Telco 完成一个可复现的 MVP，并明确它是横截面代理案例。
2. 获得合法的统一 account_id 和时间字段后，再将工单聚合到客户粒度。
3. 若为教学而生成模拟云字段，固定随机种子、记录生成规则，并把模拟结果与真实字段分开评估。

| --- | ---: | --- |

## 8. 关键风险、限制与治理

- **标签和时间泄漏**：取消后的退款、终止原因或未来账单不能作为预测特征；所有特征必须在观察截止日可获得。
- **公开代理数据的外推风险**：Telco 客户行为与 Azure 企业订阅并不等价；结果只能说明方法在该数据上的表现。
- **时间字段不足**：没有快照日期就无法严格完成时间切分、趋势特征和可靠的 BG/NBD；应把限制写进报告，而不是伪造日期。
- **类别不平衡**：SMOTE/ADASYN 只能在训练折内使用，否则会把测试信息带入训练；同时报告 PR-AUC、召回率和业务成本。
- **CLV 假设**：BG/NBD 和 Gamma-Gamma 需要交易频率、最近交易、观察期和金额等数据；不满足条件时应使用简化的订阅 CLV 并披露假设。
- **因果误读**：预测“谁会流失”不等于证明某个行动能挽留他；行动效果应通过随机实验或明确的因果设计验证。
- **隐私和成本**：客户 ID 应脱敏，密钥不得进 Git；使用 Azure Free Tier 前要设置预算和资源清理规则。
